1引言：为什么需要 vLLM？

当你用 ChatGPT 聊天时，背后发生的事情远比想象中复杂。大语言模型（如 LLaMA、Qwen）动辄数十亿甚至上百亿参数，直接用 HuggingFace Transformers 库做推理，会遇到三个致命瓶颈：

痛点 1：KV Cache 吃光显存
Transformer 自回归生成时，每生成一个 token 都要缓存之前所有 token 的 Key 和 Value 向量。以 LLaMA-70B 处理 4K 上下文为例，仅 KV Cache 就需要约 50GB 显存——比模型权重本身还大。
痛点 2：静态批处理效率低下
传统方法把多个请求打包成一个 batch，必须等最长的请求完成才能释放资源。短请求被迫等待长请求，GPU 大量时间在「陪跑」。
痛点 3：显存碎片严重
传统方法为每个请求预分配最大长度的连续内存。当请求长度参差不齐时，实际显存利用率可能不到 50%。

vLLM（Very Large Language Model inference engine）由 UC Berkeley Sky Computing Lab 开发，通过两项核心创新——PagedAttention 和连续批处理（Continuous Batching）——一举解决了上述问题，将推理吞吐量提升了 2-24 倍，同时大幅降低显存占用。

指标HuggingFace TransformersvLLM提升幅度
推理吞吐量 (tokens/s)~180~4,32024 倍
显存占用 (GB)~16.5~12.5节省 24%
平均延迟 (ms/token)~5.5~0.8降低 85%
最大并发数~8128+16 倍

接下来，我们将逐一拆解 vLLM 实现这些性能飞跃的核心组件。

2整体架构概览

vLLM 采用分层架构，每一层职责清晰、边界明确。可以用一个「高速公路系统」的类比来理解：

  • 收费站（Entrypoints）：用户请求从这里进入系统
  • 交通指挥中心（Scheduler）：决定哪些请求优先处理、如何组队
  • 分页停车场（PagedAttention）：高效管理 KV Cache 内存
  • 高速车道（Workers）：GPU 实际执行模型计算
  • 调度引擎（LLM Engine）：协调一切的大脑
图 2-1：vLLM 五层架构总览，从上到下依次为入口层、引擎核心、调度与内存管理、执行器、底层 Worker
设计哲学
vLLM 的核心设计目标是：让 GPU 始终处于高负载状态，绝不浪费一个计算周期。所有组件都围绕这一目标协作——调度器确保 batch 永远饱满，PagedAttention 确保显存零浪费，执行引擎确保计算高效。

3前置基础：Transformer 架构与 LLM 推理两阶段

在深入 vLLM 的 PagedAttention、调度器等核心组件之前，我们需要先理解两个底层概念：Transformer 的自注意力机制（Q/K/V 从何而来）和 LLM 推理的两个阶段（Prefill 与 Decode）。它们是理解 vLLM 一切优化策略的地基。

3.1 Transformer decoder-only 架构

现代 LLM（GPT / LLaMA / Qwen 等）均采用 decoder-only Transformer 结构。数据流为：输入 tokens → 词嵌入 → N 层 Transformer Block 堆叠 → 输出下一个 token 的概率分布。

每一层 Transformer Block 内部包含两个子模块：

  • Masked Self-Attention：序列中每个 token「看」其他 token，建模词与词之间的关系。Q、K、V 的计算就发生在这里，它是 KV Cache 产生的源头。
  • Feed-Forward Network (FFN)：对每个位置独立做非线性变换，是模型参数量大头（通常 3× hidden_dim，使用 SwiGLU 门控激活）。
图 3-1：Transformer decoder-only 架构，数据从输入 tokens 流经 N 层 Block 到输出概率分布

3.2 自注意力机制：Q/K/V 三矩阵

在 Self-Attention 内部，每个 token 的 embedding 分别乘以三个不同的权重矩阵（W_Q、W_K、W_V），产生三种角色不同的向量：

矩阵角色直觉类比
Q (Query)「我在找什么」搜索关键词
K (Key)「我的标签是什么」书架上的分类标签
V (Value)「我的实际内容」书的具体内容

计算流程分为三步：Q 与 K 做点积得到注意力分数（衡量 token 间的关联强度），经缩放和 softmax 归一化后，再与 V 加权求和得到注意力输出。

图 3-2：Q/K/V 计算全流程——输入向量经三个权重矩阵投影后，Q·K^T 得到注意力分数，加权 V 得到输出
最关键的一点
一旦某个 token 被处理过，它的 K 和 V 向量就不再改变。后续 token 只需要拿自己的 Q 去和这些已存的 K 做点积——这是 KV Cache 能省掉重复计算的理论基础。理解了这一点，就能自然地进入 LLM 推理的两阶段。

3.3 LLM 推理两阶段：Prefill 与 Decode

LLM 推理被拆分为两个计算特征截然不同的阶段：Prefill（预填充）和 Decode（解码）。

Prefill 阶段：一次性并行处理整个输入 prompt，为每个 token 计算 K、V 并写入 KV Cache，产出第一个输出 token。这是 compute-bound（计算密集型）阶段——大矩阵乘法，GPU 利用率高（70%-90%），只执行一次。

Decode 阶段：每次只输入 1 个新 token（上一步的输出），只计算新 token 的 Q/K/V，与 KV Cache 中已有的 K 做注意力，追加新 K/V 到缓存，产出下一个 token。这是 memory-bound（内存带宽密集型）阶段——极小矩阵乘法，GPU 利用率低（1%-10%），循环执行 N 次（N = 输出 token 数），是主要耗时来源。

图 3-3：Prefill（左）并行处理所有输入 token 并填充 KV Cache；Decode（右）逐 token 生成，每步只算 1 个 token

3.4 两阶段的衔接：KV Cache 是桥梁

两个阶段并非孤立——KV Cache 是连接它们的桥梁。Prefill 中 KV Cache 被创建，Decode 中被读取和追加，贯穿整个推理过程。这个数据结构只增不减，随着输出变长持续占用显存。

图 3-4：完整推理生命周期——Prefill 产出 KV Cache 和首个 token，Decode 循环消费缓存并逐 token 生成
从基础到 vLLM：为什么这些知识很重要
理解了 Transformer → Q/K/V → Prefill/Decode → KV Cache 这条知识链，就能明白 vLLM 要解决的核心问题：KV Cache 占显存太大（→ PagedAttention 分页管理）、Decode 阶段 GPU 利用率太低（→ 连续批处理）、不同请求的 KV Cache 大小不一（→ 调度器动态分配与抢占）。接下来各节将逐一拆解这些优化机制。

4KV Cache 机制：推理的「记忆」

4.1 什么是 KV Cache？

要理解 vLLM，首先得理解 KV Cache——它是 LLM 推理中最关键的内存结构。

Transformer 模型使用自注意力机制（Self-Attention）计算 token 之间的关系。对于序列中的每个 token，模型会生成三个向量：Q（Query）、K（Key）和V（Value）。注意力分数由 Q 和 K 的点积计算，再用它对 V 加权求和。

关键洞察是：在自回归生成中，已生成 token 的 K 和 V 向量不会改变。当生成第 N 个 token 时，前 N-1 个 token 的 K、V 向量与上一步骤完全相同。如果每步都重新计算它们，会浪费大量算力。

KV Cache 就是把这些 K、V 向量缓存起来，避免重复计算。每生成一个新 token，只需计算新 token 的 K、V 并追加到缓存中即可。

图 4-1：KV Cache 在 Prefill 阶段初始化，在 Decode 阶段逐步增长

4.2 KV Cache 的显存开销有多大？

KV Cache 的大小取决于模型结构和序列长度，计算公式为：

KV Cache 大小 = 2 × num_layers × seq_len × num_kv_heads × head_size × dtype_bytes

以 LLaMA-70B（80 层、8 个 KV head、head_size=128、bf16）处理 4K 上下文为例：

2 × 80 × 4096 × 8 × 128 × 2 bytes ≈ 40 GB

这意味着仅 KV Cache 就需要 40GB 显存——而模型权重本身约 140GB（bf16）。在多请求并发场景下，KV Cache 的总占用会迅速膨胀，成为推理瓶颈。

图 4-2：GPU 显存分配比例，KV Cache 是仅次于模型权重的第二大内存消耗者
关键认知
KV Cache 是 vLLM 一切优化的出发点。PagedAttention 解决的是「KV Cache 怎么存」，调度器解决的是「KV Cache 给谁用」，执行引擎解决的是「KV Cache 怎么算」。理解了 KV Cache，就理解了 vLLM 的一半。

5PagedAttention：内存管理的革命

5.1 传统方法的内存浪费

传统推理框架（如 HuggingFace Transformers）为每个请求预分配一段连续的、按最大长度计算的内存。这就像酒店管理——不管你住几晚，都得订一整个房间。

问题在于，请求长度千差万别。假设 batch 中有 3 个请求，实际长度分别为 100、300、500，但都按 500 预分配，实际利用率仅 60%。更糟的是，内部碎片（预留未用空间）和外部碎片（请求释放后留下的不连续空洞）会进一步蚕食可用内存。

图 5-1：传统连续分配（左）造成 40% 浪费，PagedAttention（右）通过分块映射实现 96%+ 利用率

5.2 操作系统分页类比

PagedAttention 的灵感直接来自操作系统的虚拟内存分页机制。如果你学过 OS 课程，这个类比会让你豁然开朗：

OS 虚拟内存vLLM PagedAttention对应关系
进程的虚拟地址空间一个请求的逻辑 KV Cache 序列请求看到的「连续」KV Cache
物理页 (Page)KV Cache 块 (Block，默认 16 tokens)固定大小的物理存储单元
页表 (Page Table)块表 (Block Table)逻辑块号 → 物理块号的映射
物理内存GPU 显存中的 KV Cache 池所有请求共享的存储池
缺页中断块分配不足 → 触发抢占内存不够时的处理机制
共享内存Prefix Caching（前缀共享）多个请求共享相同前缀的 KV 块

5.3 PagedAttention 的工作流程

  1. 初始化：系统启动时，根据 GPU 可用显存计算出能容纳多少个 KV Cache 块（num_gpu_blocks），预分配整个块池
  2. 请求到达：新请求进入 Prefill 阶段，调度器从块池中为其分配足够的块
  3. 块表映射：为该请求创建块表，记录逻辑块号到物理块号的映射关系
  4. 注意力计算：CUDA 内核通过块表查找物理块位置，在非连续的物理块上计算注意力
  5. 动态增长：每生成 16 个 token（一个块的大小），分配一个新块并更新块表
  6. 块释放：请求完成后，其所有块归还到空闲池，立即可被其他请求复用

5.4 前缀缓存（Prefix Caching）

在实际应用中，很多请求共享相同的前缀——比如系统提示词（system prompt）、few-shot 示例等。PagedAttention 允许这些请求共享同一组物理块，通过引用计数管理。

图 5-2：多个请求共享相同前缀的物理块，通过引用计数管理共享关系

5.5 块大小的影响

块大小（block_size）是 PagedAttention 的关键参数，默认为 16：

  • 太小（如 4）：块表变大，元数据开销增加，CUDA 内核需要更多间接寻址
  • 太大（如 64）：最后一块的内部碎片增大，内存利用率下降
  • 默认 16：在元数据开销和碎片率之间取得平衡，适合大多数场景

每个块的实际内存大小计算公式：

block_bytes = 2 (K+V) × block_size × num_kv_heads × head_size × dtype_bytes

# 示例: LLaMA-7B, block_size=16, 32 KV heads, head_size=128, bf16
# block_bytes = 2 × 16 × 32 × 128 × 2 = 262,144 bytes = 256 KB
论文数据
根据 vLLM 论文（SOSP '23）的实验，PagedAttention 将 KV Cache 内存利用率从传统方法的 20-38% 提升至 96.3%，几乎实现了「零浪费」。这意味着相同硬件上可以同时处理更多的并发请求。

6调度器（Scheduler）：交通指挥中心

6.1 调度器的作用

如果说 PagedAttention 解决了「内存怎么存」的问题，那么调度器解决的是「内存和算力给谁用、什么时候用」的问题。

调度器的核心职责是：在每个推理步骤（step）之前，决定本次前向传播处理哪些请求。它就像高速公路上的交通指挥中心，时刻决定哪些车（请求）可以上路、哪些需要让行。

6.2 三大队列：请求的生命周期

vLLM 调度器维护三个队列来管理所有请求：

队列状态说明优先级
Running 正在生成 已完成 Prefill，正在 Decode 生成 token 的请求 最高（不能让用户等太久）
Waiting 等待处理 新到达、尚未开始 Prefill 的请求 最低（新来的先排队）
Swapped 被换出 因显存不足被抢占，KV Cache 已转移到 CPU 内存 中等（需尽快恢复）
图 6-1：调度器维护三大队列，请求在队列间流转，每步按优先级调度

6.3 连续批处理（Continuous Batching）

连续批处理是 vLLM 高吞吐的关键。与传统静态批处理不同，它在每个推理步骤重新决定 batch 组成：

特性静态批处理连续批处理 (vLLM)
调度时机每个 batch 一次每个 token（每步）一次
请求加入必须等当前 batch 全部完成随时可以加入
请求退出必须等最长请求完成完成即退出，释放资源
GPU 利用率低（空位无法填补）高（空位立即被新请求填补）
类比大巴车：满员发车，到终点才下车公交车：每站可上可下
图 6-2：静态批处理（左）存在空位浪费，连续批处理（右）动态填补空位

6.4 抢占机制（Preemption）

当所有 Running 请求的 KV Cache 同时增长，显存可能不够用。此时调度器会触发抢占——暂停某些请求，释放其 KV Cache 空间给更高优先级的请求。vLLM 有两种抢占策略：

策略原理优点缺点版本
Recompute（重计算） 丢弃被抢占请求的所有 KV 块，将其放回 Waiting 队列。恢复时重新执行 Prefill 无需 CPU↔GPU 传输，释放内存即刻完成 恢复时需重新计算 Prefill，浪费算力 V1 默认
Swap（换出） 将被抢占请求的 KV 块复制到 CPU 内存，恢复时再复制回 GPU 保留计算结果，恢复时无需重算 PCIe 传输带宽开销，占用 CPU 内存 V0 默认
注意：抢占风暴（Thrashing）
如果 max_num_seqs 设置过大，导致请求频繁被抢占又恢复，系统会陷入「抢占风暴」——大量时间花在换入换出/重计算上，吞吐量骤降，P99 延迟飙升。这类似于操作系统的页面抖动。解决方案：合理设置 max_num_seqs 和 gpu_memory_utilization，保留一定的内存余量。

6.5 Chunked Prefill：避免长请求阻塞

一个长 prompt（如 32K tokens）的 Prefill 是计算密集型操作，如果在一个步骤内全部处理，会阻塞所有正在 Decode 的请求——这就是队头阻塞（Head-of-Line Blocking）。

Chunked Prefill 将长 prompt 切分成多个 chunk（受 max_num_batched_tokens 限制），每个步骤只处理一个 chunk，并与其它请求的 Decode 混合执行。这样长请求的 Prefill 分散在多个步骤中，不会阻塞其他请求的 token 生成。

图 6-3：Chunked Prefill 将长 prompt 分块，与 Decode 混合执行，避免队头阻塞

7模型执行引擎：GPU 上的实干家

7.1 执行层级结构

调度器做出决策后，需要有人真正在 GPU 上执行计算。这就是执行引擎的职责。vLLM 的执行层采用三级结构：

图 7-1：执行引擎三级结构，职责逐层细化

Executor（执行器）

执行器是引擎与 GPU 之间的桥梁，负责管理 Worker 进程。根据部署模式不同，有三种实现：

  • UniProcExecutor：单进程执行，Worker 与引擎在同一进程中。适合单 GPU 开发调试
  • MultiprocExecutor：多进程执行，每张 GPU 对应一个独立 Worker 进程。提供更好的隔离性
  • RayGPUExecutor：基于 Ray 的分布式执行，支持跨节点多 GPU。适合大规模集群部署

Worker（工作器）

每个 Worker 绑定一张 GPU，负责三件大事：

  1. 初始化设备：分配 CUDA 设备、验证显存是否充足、设置分布式配置（TP/PP/DP）
  2. 加载模型：实例化模型架构、加载权重、调用 model.eval()
  3. 初始化 KV Cache：运行性能分析前向传播、计算可用显存能容纳多少 KV 块、分配并绑定 KV Cache 张量

ModelRunner（模型运行器）

ModelRunner 是真正执行前向传播的组件，核心流程：

  1. _prepare_inputs()：根据调度器输出，准备 input_ids、positions、注意力元数据（包括块表）
  2. execute_model()：调用模型的 forward() 方法，执行前向传播，得到 logits
  3. sample()：根据采样参数（temperature、top_p 等）从 logits 中采样下一个 token
  4. 返回结果：将采样的 token 和相关元数据返回给引擎

7.2 GPU 显存管理

vLLM 启动时的显存分配过程非常精巧：

1. 加载模型权重         → 占用约 60-65% 显存
2. 运行 dummy forward   → 测量激活内存（约 5%）
3. 计算可用 KV Cache 空间 = 总显存 × gpu_memory_utilization - 权重 - 激活
4. 计算可容纳的块数      = 可用空间 / 每块大小
5. 预分配所有 KV Cache 块 → 占用约 25-30% 显存

关键参数 gpu_memory_utilization（默认 0.9）控制 vLLM 最多使用多少比例的 GPU 显存。预留的 10% 作为安全余量，防止 OOM。

7.3 CUDA Graph 优化

每次前向传播涉及大量 CUDA 内核启动，每次启动都有固定开销（约 10-50 微秒）。对于 Decode 阶段（每次只生成一个 token，计算量很小），内核启动开销占比很高。

CUDA Graph 将整个前向传播的计算图「录制」下来，后续直接「回放」，跳过内核启动开销：

  • 录制阶段：对常见的 batch size 运行一次模拟前向传播，将 GPU 操作序列录制为 DAG
  • 回放阶段：实际推理时，直接启动预先录制的图，用新输入替换旧输入
  • 效果：Decode 阶段延迟降低 20-40%，尤其对小 batch 效果显著
何时禁用 CUDA Graph？
如果模型结构动态变化（如变长输入需要不同 shape），或使用了不兼容 CUDA Graph 的自定义算子，可以通过 --enforce-eager 禁用 CUDA Graph，回退到即时执行模式。

7.4 分布式执行

对于大模型（如 70B+），单张 GPU 无法容纳，需要多卡并行。vLLM 支持两种并行策略：

并行策略原理适用场景
张量并行 (TP) 将每一层的权重矩阵切分到多张 GPU 上，每张卡计算一部分，通过 All-Reduce 汇总结果 同节点多 GPU，延迟低
流水线并行 (PP) 将模型的不同层分配到不同 GPU 上，请求像流水线一样依次经过各卡 跨节点部署，模型极大

Worker 之间通过 NCCL（NVIDIA Collective Communications Library）或 Ray 进行通信和同步。

8.5 AsyncLLMEngine：异步引擎

API Server 使用 AsyncLLMEngine 包装核心 LLMEngine，提供异步接口：

  • 异步请求队列：多个 HTTP 请求可以并发提交，引擎内部排队处理
  • 流式输出：每生成一个 token 就通过 SSE（Server-Sent Events）推送给客户端，用户看到逐字输出效果
  • 异步输出处理：V1 架构支持将 GPU→CPU 的输出拷贝与下一步计算重叠，进一步提高吞吐
V0 与 V1 架构
vLLM 正在从 V0 架构向 V1 架构迁移。V1 的主要改进包括：默认使用 Recompute 抢占（而非 Swap）、更高效的调度器、异步输出处理、改进的 Prefix Caching。V1 在多数场景下比 V0 快 1.7 倍。可以通过 VLLM_USE_V1=1 环境变量启用。

现在让我们把所有组件串联起来，跟踪一个用户请求从到达到完成的完整生命周期：

图 9-1：一个请求从到达到完成的完整流程，步骤 3-7 在每个 token 生成时循环执行
循环的关键
步骤 3 到 7 构成了一个迭代循环：每生成一个 token，调度器重新调度、分配内存、执行模型、采样输出。这个循环一直持续到请求完成。多个请求的 token 生成在同一循环中交替进行，这就是连续批处理的本质。

10学习路径与建议

对于零基础读者，建议按以下路径循序渐进地学习 vLLM：

1

建立基础知识储备

先理解 Transformer 架构和自注意力机制，搞清楚 Q/K/V 是什么。了解 LLM 推理的两个阶段：Prefill（处理输入）和 Decode（生成输出）。

推荐资源：3Blue1Brown 的 Transformer 可视化视频、Jay Alammar 的《The Illustrated Transformer》

2

理解 KV Cache 的概念

动手用 HuggingFace Transformers 跑一个小模型（如 opt-125m），观察推理过程中显存的变化。思考：为什么生成越长越慢？为什么 batch 越大越吃显存？

实践：nvidia-smi -l 1 监控显存，对比 Prefill 和 Decode 阶段的显存变化

3

学习操作系统分页机制

PagedAttention 的核心类比就是 OS 虚拟内存。理解页表、物理页、逻辑地址、缺页中断等概念，会让你对 PagedAttention 豁然开朗。

推荐资源：OSTEP（Operating Systems: Three Easy Pieces）第 20-21 章

4

阅读 vLLM 论文

论文《Efficient Memory Management for Large Language Model Serving with PagedAttention》（SOSP '23）是理解 vLLM 设计的最佳起点。重点关注 PagedAttention 的设计动机和实验数据。

重点：Figure 2（内存浪费对比）、Figure 4（PagedAttention 架构图）、Figure 8（性能对比）

5

动手部署 vLLM

用一个 7B 模型（如 Llama-3-8B-Instruct）在本地启动 vLLM 服务，用 OpenAI SDK 调用。调整 max-num-seqs、gpu-memory-utilization 等参数，观察吞吐和延迟的变化。

pip install vllm
vllm serve meta-llama/Llama-3-8B-Instruct --port 8000
6

阅读核心源码

按以下顺序阅读源码，建立从宏观到微观的理解：

  • vllm/engine/llm_engine.py → 理解引擎主循环
  • vllm/core/scheduler.py → 理解调度逻辑和三大队列
  • vllm/core/block_manager.py → 理解 PagedAttention 的块管理
  • vllm/worker/model_runner.py → 理解模型执行流程
  • vllm/attention/backends/ → 理解注意力内核实现
7

性能调优实战

使用 vllm bench 工具进行基准测试，理解关键参数的影响：

  • max-num-seqs：控制并发数，影响吞吐和延迟的权衡
  • max-num-batched-tokens：控制每步 token 数，影响 Chunked Prefill 行为
  • gpu-memory-utilization：控制显存使用比例，留余量防 OOM
  • block-size：KV Cache 块大小，通常保持默认 16
  • enable-prefix-caching：开启前缀缓存，适合多轮对话场景
8

探索高级特性

在掌握基础后，可以进一步学习：

  • 推测解码（Speculative Decoding）：用小模型预生成候选 token，大模型并行验证
  • 多 LoRA 动态加载：一个模型实例服务多个微调版本
  • 分离式 Prefill/Decode：Prefill 和 Decode 在不同 GPU 池上执行
  • 多模态推理：支持图像、视频等输入
  • V1 架构：了解 vLLM 最新架构改进
学习心法
  1. 先跑通再深究：先用起来，产生感性认识，再读论文和源码
  2. 画图辅助理解：自己画一遍请求流程图、内存分配图，比读十遍文档有效
  3. 对比学习：对比 vLLM 与 TGI、TensorRT-LLM、SGLang 的设计差异，理解不同 trade-off
  4. 关注社区：vLLM 更新很快，关注 GitHub Discussions 和官方博客获取最新信息

★核心要点总结

组件核心职责关键创新性能影响
KV Cache 缓存已计算 token 的 K/V 向量，避免重复计算 将推理从 O(n²) 降为 O(n) 显存占用 ~30%，是优化的核心对象
PagedAttention 将 KV Cache 分成固定大小块，通过块表映射管理 OS 虚拟内存分页类比，非连续存储 显存利用率 20%→96%，支持更多并发
Scheduler 每步决定处理哪些请求，管理三大队列 连续批处理 + 抢占调度 + Chunked Prefill 吞吐量提升 3-10 倍，GPU 利用率 65%→92%
Execution Engine 在 GPU 上执行模型前向传播和采样 Executor→Worker→ModelRunner 三级架构 + CUDA Graph Decode 延迟降低 20-40%，支持多 GPU 分布式
API Server 提供 OpenAI 兼容的 HTTP 接口 AsyncLLMEngine + 流式输出 + FastAPI 零代码迁移，直接替换 OpenAI API 调用
一句话理解 vLLM
vLLM 通过 PagedAttention（让显存零浪费）+ 连续批处理（让 GPU 零空闲）+ CUDA Graph（让内核启动零开销），实现了大语言模型推理的极致性能。它的设计哲学是：让每一比特显存、每一个计算周期都物尽其用。
